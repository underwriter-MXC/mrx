> **Educational document-control boundary.** This article provides an organizational template for a possible mineral-rights sale package. It does not authenticate a document or determine title, ownership, acreage, authority, delivery, acknowledgment, validity, recordability, enforceability, contract meaning, value, offer fairness, payment, closing, tax basis, tax treatment, or whether to sell. Use qualified legal, title, tax, accounting, appraisal, land, and closing professionals for owner-specific conclusions. MRX may have an economic interest in a later transaction; when that applies, the buyer relationship is disclosed in writing before an agreement is signed.

A mineral rights sale document package index is a page-level manifest of exactly what you received. It identifies each source file, counts its pages, lists every referenced exhibit and schedule, connects signature and execution copies, and records later replacements without overwriting the original package.

Its job is narrow: **package identity and completeness**. A clean index can show that a referenced exhibit was not included or that two versions contain different page counts. It cannot tell you whether either version is authentic, operative, legally sufficient, recordable, fair, or safe to sign.

## Keep the index separate from the decision log

The index answers, “What is in this package, and is every referenced component present?” The separate [mineral-rights sale decision log](/blog/mineral-rights-sale-decision-log/) answers, “What changed, which question remains open, who owns the next action, and which later entry supersedes an earlier one?”

Do not merge the two jobs. The package index should not assign negotiation decisions, evaluate an offer, interpret a clause, or tell someone what to do next. It can link to a decision-log entry when a missing item creates a question, but the index itself remains an inventory.

The broader [seller-control process](/blog/selling-mineral-rights-selling-process-for-mineral-owners/) also remains separate. That guide organizes transaction stages from first contact through written proposals, diligence, signing, funding, delivery, recording, and retained records. The index is one controlled artifact inside that larger process.

## Freeze the package as received

Start with the original delivery before opening working copies across several apps or forwarding files to other people.

Create a package ID such as `PKG-2026-08-15-01`, then record:

- received date and time, including the time zone;
- sender and delivery channel as observed;
- original filename, extension, and file size;
- container type, such as one PDF, a ZIP archive, or several attachments;
- access restrictions or password handling location, without placing the password in the index;
- the original file's storage location and read-only status;
- an optional cryptographic file hash for later identity checking; and
- the person who performed the intake.

Preserve that original even if it contains blank pages, a sideways scan, duplicated sheets, or an inconvenient filename. Make corrections only in a separately labeled working copy. The original shows what arrived; the working copy supports review.

If the delivery contains several files, give the delivery one package ID and every file its own component ID. That prevents a later reader from treating one convenient PDF as the entire package when the email also carried a separate exhibit or addendum.

## Build one row for every source file

For each file, record a stable component ID and the fields another person would need to find and reconcile it:

1. **Source filename.** Preserve the filename exactly as received.
2. **Document label.** Record the title or label as written on the document without converting it into a legal conclusion.
3. **Document date.** Record a visible date as written and distinguish it from the received date.
4. **Parties as written.** Transcribe the named parties for matching only; do not conclude identity, authority, or capacity.
5. **Stated page count.** Capture “Page 1 of 12” or a table-of-contents count when present.
6. **Actual page count.** Count every page in the received file, including blank, cover, notary, and attachment pages.
7. **First and last page labels.** These provide a quick boundary check.
8. **Referenced components.** List every exhibit, schedule, addendum, amendment, rider, appendix, annex, attachment, incorporated term, or separate instruction named by the file.
9. **Presence status.** Use present, missing, partial, unreadable, duplicated, separate-file match pending, or not located.
10. **Signature status.** Describe only what is visible: unsigned copy, signature page present, electronic completion record received, or signature image present. Do not decide whether a signature is genuine or effective.
11. **Replacement status.** Identify any later file the sender says replaces this one, while preserving both.

Use “not shown” or “not located” instead of guessing. An honest blank field is stronger completeness evidence than a confident assumption.

## Reconcile pages before attachments

Perform a page-by-page pass for each source file. Assign a position such as `F03-P001`, record the printed page number if one appears, and note a neutral page type: cover, body, signature, acknowledgment, exhibit divider, schedule, blank, or other.

Then compare three counts:

- the file's digital page count;
- the highest printed page number or stated total; and
- the index's number of inventoried pages.

Those counts may differ for ordinary reasons. A cover page may have no printed number. An exhibit may restart numbering. A notary page may follow “Page 8 of 8.” The index should expose the difference, not repair it silently.

A reconciliation note might say: “Received PDF contains 14 digital pages. Main document displays pages 1 through 8. Exhibit A displays pages 1 through 4. One unnumbered signature page and one unnumbered acknowledgment page are present.” That is an observable inventory statement. It does not say the package is legally complete.

Mark a page unreadable when the scan prevents reliable inventory. Do not reconstruct missing words, dates, names, legal descriptions, or signatures from context. Request a clearer source copy through the separate communication or decision workflow.

## Trace every cross-reference

After the page count balances, search the package for cross-reference words such as exhibit, schedule, addendum, amendment, appendix, attachment, annex, rider, incorporated, online terms, closing instruction, and separate agreement.

Create one cross-reference row for each item:

- the source component and page where it is referenced;
- the referenced label exactly as written;
- whether the item is embedded, delivered as a separate file, or not located;
- the matched component ID, if found;
- the visible revision or date, if any; and
- a neutral discrepancy note.

The [hidden-traps guide](/blog/the-hidden-traps-in-selling-mineral-rights/) explains why cross-document review matters when definitions, exhibits, adjustments, deadlines, or instructions interact. The package index stops one step earlier. It confirms whether the pieces are available for review; it does not interpret what those pieces do.

Do not infer that a file called “Exhibit A” matches every “Exhibit A” reference. Compare the document label, described subject, page count, visible date, revision marker, and delivery context. If the match is uncertain, record “possible match; review required.”

## Connect signature and execution records without drawing conclusions

A package may contain an unsigned draft, a signed counterpart, a notarized copy, an electronic-signature completion certificate, a closing copy, and a recorded image. Give each one a separate component ID.

For each version, record only observable facts:

- which pages are included;
- which signature blocks contain visible marks;
- which names and capacities are printed as written;
- whether an acknowledgment page is present;
- whether an electronic completion record is a separate file;
- whether the sender labels the copy executed, final, closing, or recorded; and
- any recording reference printed on the received image.

Texas Property Code [Chapter 5](https://statutes.capitol.texas.gov/Docs/PR/pdf/PR.5.pdf) addresses conveyances, and [Chapter 12](https://statutes.capitol.texas.gov/Docs/PR/pdf/PR.12.pdf) addresses recording instruments concerning property. Those statutes concern the actual instrument and its circumstances. A private index cannot determine whether a particular mineral document satisfies applicable requirements, was delivered, has legal effect, or may be recorded. A qualified Texas attorney or title professional should answer those questions for the actual package.

The [Texas step-by-step selling guide](/blog/how-the-step-by-step-process-of-selling-texas-mineral-rights-works/) likewise treats signing, payment, deed delivery, and recording as distinct events. The index may inventory evidence associated with each event. It must not collapse them into a single “closed” status.

## Record replacements as new package versions

When a corrected file arrives, do not overwrite the earlier one. Create a new package receipt or component version and record:

- the new received time and source filename;
- the sender's statement about what it replaces;
- the earlier package and component IDs;
- the new page-count reconciliation;
- added, removed, or relabeled attachments as observed; and
- whether a complete refreshed package or only one replacement component was received.

If only a revised exhibit arrives, do not assume every copy of the main document now incorporates it. Record the delivery relationship and let qualified reviewers determine which documents control.

A simple version chain might read `PKG-01/F04 → sender-stated replacement PKG-02/F02`. Avoid labels such as “valid version,” “binding version,” or “final legal version” unless that wording is part of an identified qualified professional conclusion kept outside the index.

## Use a fictional completeness audit

Suppose a delivery contains a 10-page agreement PDF and a separate 3-page exhibit PDF. The agreement's contents page lists Exhibit A and Schedule 1, but the delivery contains no Schedule 1. Page 6 refers to an addendum that is also not present.

The index could record:

- package file count: 2;
- agreement digital pages: 10; inventoried pages: 10;
- Exhibit A digital pages: 3; inventoried pages: 3;
- Exhibit A: separate-file match located, component `F02`;
- Schedule 1: referenced, not located in the delivery;
- addendum: referenced on agreement page 6, not located; and
- package status: page counts reconciled, two referenced components not located.

That audit supports a precise request for the missing components. It does not decide whether the agreement is incomplete as a matter of law, whether the missing items are material, or whether anyone should sign.

## Restrict tax and private records

IRS [Publication 544](https://www.irs.gov/publications/p544) explains that basis and adjusted basis are used in determining gain or loss from a sale or other disposition. IRS [Publication 551](https://www.irs.gov/publications/p551) explains basis concepts and the need for accurate records of items that affect basis.

The package index may identify the existence and restricted storage location of relevant acquisition, inheritance, improvement, depletion, disposition, or closing records. It should not expose taxpayer identifiers or account details in a broadly shared manifest. It also cannot determine which records affect a particular mineral interest, allocate basis, calculate gain, classify a transaction, select a reporting position, or prescribe a retention period. Put those questions in a qualified tax professional's workflow.

## Run a final completeness check

Before handing the package to a reviewer, confirm that:

- every received source file has a component row;
- every digital page has an inventory position;
- stated, printed, digital, and inventoried page counts are reconciled or explained;
- every referenced exhibit, schedule, addendum, amendment, appendix, rider, attachment, and incorporated item has a presence status;
- unsigned, signed, acknowledgment, electronic-execution, closing, and recorded copies remain distinguishable;
- later replacements point back to preserved earlier versions;
- originals and working copies are stored separately;
- sensitive records are restricted and shared only as needed; and
- the index contains no conclusions about authenticity, authority, title, validity, legal effect, recordability, value, tax, payment, closing, or whether to sell.

The result should let another person answer, “What exactly was received, where is it, and which referenced pieces are missing or uncertain?” If the index answers more than that, it has probably drifted into a different professional or decision workflow.

## Frequently asked questions

### What is a mineral rights sale document package index?

It is a page-level manifest of the source files and components received for a possible sale, including page counts, document dates, parties as written, exhibits, schedules, addenda, amendments, incorporated items, signature copies, execution records, and replacements. It records package completeness without interpreting the documents.

### Should blank and duplicate pages be listed?

Yes. Give each physical or digital page a position and status, including intentionally blank, duplicate, unreadable, or apparently missing. That preserves the package as received and makes later reconciliation inspectable.

### Does a complete index mean the documents are valid or enforceable?

No. Completeness does not prove authenticity, signer authority, delivery, acknowledgment, validity, enforceability, title, legal effect, recordability, payment, or closing. Qualified professionals must review the actual instruments for those questions.

### What should happen when a revised exhibit arrives?

Preserve the earlier package, add the revised file as a new received version, identify which prior component the sender says it replaces, and reconcile the new page and attachment counts. Do not overwrite the original or decide which version controls.

### Should tax records be part of the package index?

The index may identify tax or basis records kept in a restricted location and note the professional workflow they support. It should not expose sensitive identifiers, classify the interest, determine basis, calculate gain, choose tax treatment, or prescribe a retention period.
